# v0.2.0 — Ship what exists, truthfully

Read [../ROADMAP.md](../ROADMAP.md) first for why this release comes before the
capability work.

## Goal

Everything in this repository already works well enough to be worth installing,
and nobody can install it: `https://pypi.org/pypi/nebius-mcp/json` returns 404
while `README.md` documents `uvx nebius-mcp`. This release publishes the
package, deletes every claim the code does not support, and closes the two
safety defects that are cheap to fix and expensive to leave. It adds no new
Nebius capability.

The measure of success: a stranger following the README reaches a successful
`iam_whoami`, and every sentence they read on the way is true.

## Scope

### In

- PyPI publication with a tag-driven, token-free release workflow.
- A CI gate that fails when documentation disagrees with the running server.
- Correcting the false security claims in `src/nebius_mcp/confirm.py` and
  `src/nebius_mcp/tools/secrets.py`, and reclassifying `secrets_reveal_payload`.
- Closing the redaction bypasses on `cloud_init_user_data`, camelCase keys, PEM
  blocks and presigned-URL signatures.
- Routing the error path and the audit log through the sanitizer.
- A stdio transport regression test.
- Finishing the command-line front door started in the working tree.

### Out, deliberately

- Any new Nebius operation. No creates, no updates, no kubeconfig. Those are
  v0.3.0.
- Token Factory. That is v0.4.0 and needs an HTTP client the project does not
  have.
- Toolsets and schema-size reduction. v0.3.0, alongside the tools that make the
  surface grow.
- Retries, idempotency keys, rate limiting. v0.4.0; retries are blocked on a
  call-path rewrite that is too large for this release.
- A policy file. v0.3.0, paired with the write coverage that makes it
  load-bearing.
- Live integration tests. v0.4.0. This release does not require a Nebius
  account to complete.
- A documentation site. v1.0.0.

### v0.2.0-T4 — Reclassify `secrets_reveal_payload` and gate it independently (S)

`list_tools()` reports `{'readOnlyHint': True, 'destructiveHint': False,
'idempotentHint': True, 'openWorldHint': True}` on the one tool in the server
that returns plaintext secrets by design. Any client running
auto-approve-read-only exfiltrates secrets with no prompt. The module docstring
at `src/nebius_mcp/tools/secrets.py:9-12` claims `openWorldHint=true` makes
clients prompt; that is not what `openWorldHint` means, and clients gate on
`readOnlyHint` and `destructiveHint`.

Acceptance:

1. `secrets_reveal_payload` annotations become `readOnlyHint: False`,
   `destructiveHint: True`.
2. A test iterates every tool and cross-checks a hard-coded `SENSITIVE_TOOLS`
   set, asserting no tool with `readOnlyHint: True` can return unredacted
   secret material.
3. A new environment variable `NEBIUS_MCP_ALLOW_SECRET_REVEAL`, unset by
   default; with it unset the tool raises `ToolError` and a test monkeypatching
   `client.service` asserts `PayloadServiceClient` was never constructed.
4. The tool requires the confirm-token two-step.
5. The false `openWorldHint` sentence is deleted from the module docstring, and
   so is the `secrets_get_payload_metadata` line.

Files: `src/nebius_mcp/tools/secrets.py`, `tests/unit/test_tools_secrets.py`,
`README.md`.

### v0.2.0-T5 — Close the redaction bypasses (M)

`sanitize._is_sensitive_key` lowercases the key but does not strip underscores,
so `secretKey` becomes `secretkey`, matches no exact key and contains none of
the four substrings. `InstanceSpec` exposes `cloud_init_user_data`, the most
common place people put bootstrap secrets, and `compute_get_instance` — a
`readOnlyHint: true` tool — returns it verbatim.

Acceptance:

1. Key normalization lowercases and strips underscores before matching, so
   `secretKey`, `secret_key` and `accessKeySecret` all match.
2. Exact keys added: `cloud_init_user_data`, `user_data`, `client_key_data`,
   `client_certificate_data`, `kubeconfig`, `ssh_authorized_keys`.
3. Value patterns added: PEM blocks (`-----BEGIN [A-Z ]*PRIVATE KEY-----`) and
   presigned-URL parameters (`X-Amz-Signature=`, `X-Amz-Credential=`).
4. A table-driven test in `tests/unit/test_sanitize.py` covers at least these
   nine inputs and asserts `<redacted>` for each: `secret_key`, `secretKey`,
   `accessKeySecret`, `cloud_init_user_data`, `client_key_data`, `kubeconfig`,
   a PEM header string, an `X-Amz-Signature` URL, a JWT. Seven of the nine pass
   through in the clear on today's tree; the test must be shown failing first.
5. A test asserts `redact` does not mangle a legitimate non-secret string that
   merely contains the word "secret" in prose, so the change does not silently
   corrupt descriptions.

Files: `src/nebius_mcp/sanitize.py`, `tests/unit/test_sanitize.py`.

### v0.2.0-T6 — Redact and cap the error path (S)

Errors bypass the sanitizer entirely. `errors.py:30` interpolates the raw
exception into a `ToolError`, and `audit.py` writes `str(exc)[:200]` to the log
unredacted. A gRPC error echoing request metadata, or a failure inside
`secrets_reveal_payload`, ships credentials to both the model and the operator's
log aggregator.

Acceptance:

1. `errors.to_tool_error` passes its message through `sanitize.redact` and
   truncates to a documented cap.
2. `audit.log_call` redacts the `error` field before emission.
3. Error text reaching the model carries the `DATA_PREAMBLE` framing. API error
   strings are attacker-influenceable: a resource named with an injection
   payload appears verbatim in a not-found message.
4. A test constructs an exception whose `str()` contains a JWT and
   `secret_key=abc`, then asserts both the `ToolError` message and the captured
   audit line contain `<redacted>` and neither contains the raw values.

Files: `src/nebius_mcp/errors.py`, `src/nebius_mcp/audit.py`,
`tests/unit/test_errors.py`, `tests/unit/test_audit_stream.py`.

### v0.2.0-T7 — An honest `SECURITY.md`, and delete the false security claims (M)

`src/nebius_mcp/confirm.py:11-13` calls the token flow "the spec-recommended
mitigation for tools annotated destructiveHint=True against indirect prompt
injection." It is not. The model receives the token and replays it; a token can
be minted and consumed in two consecutive in-process calls with no human
anywhere. It is a mistake guard. Overclaiming loses a security audience faster
than having no controls.

Acceptance:

1. `SECURITY.md` exists at the repository root with a supported-versions table,
   a private disclosure contact, and a threat-model section with one row per
   threat — indirect prompt injection, tool poisoning and rug pull, credential
   blast radius, secret exfiltration, audit tampering, supply-chain compromise
   — each marked mitigated, partial or not mitigated, with a `file:line` link
   to the enforcing code.
2. `src/nebius_mcp/confirm.py`'s module docstring states that the token is a
   mistake guard, not an injection defense, and says why.
3. A CI grep asserts the strings `spec-recommended mitigation` and
   `so well-behaved clients prompt the user` appear nowhere under `src/`.
4. `SECURITY.md` states plainly that `NEBIUS_MCP_MODE=write` is a single global
   boolean unlocking 46 delete verbs across 59 resource types with no scoping,
   and links the v0.3.0 policy work as the planned fix.
5. GitHub private vulnerability reporting is enabled on the repository.

Files: `SECURITY.md`, `src/nebius_mcp/confirm.py`,
`src/nebius_mcp/tools/secrets.py`, `.github/workflows/ci.yml`.

## Risks

- **PyPI name availability is unverified.** Nobody has confirmed
  `nebius-mcp` can be claimed on PyPI by this project. T1 begins by checking;
  if the name is taken, stop and escalate rather than picking a different name
  unilaterally, because the name appears in every install instruction and in
  the planned MCP registry entry.
- **T3, T4 and T7 all change hashed tool descriptions.** Land them in an order
  that records the manifest hash once, at the end, rather than three times.
- **T5 could over-redact.** `redact` walks every response. A too-broad
  substring rule will blank out legitimate fields and produce a confusing,
  hard-to-diagnose regression. The non-secret prose test in T5 exists for this.
- **T9's `--check` live probe requires credentials.** It must degrade to the
  filesystem-only report with a clear message when none resolve, and it must
  never be the reason a CI job fails.
- **Python 3.14.** The development virtual environment runs 3.14.4, outside the
  CI matrix and the classifier list. This release does not resolve it; v1.0.0
  does. Do not add 3.14 to the classifiers here without adding it to the matrix.
