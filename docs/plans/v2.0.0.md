# v2.0.0 — Shared infrastructure, and coverage that maintains itself

Read [../ROADMAP.md](../ROADMAP.md) first. This release assumes v1.0.0 shipped.

## Goal

Two shifts justify a major version.

The server stops being a per-developer process holding one ambient credential
and becomes shared infrastructure, where each caller authenticates as
themselves and the server holds no standing cloud secret. v1.0.0 removes the
process globals and ships loopback HTTP; this release turns that into something
a team can actually point at.

And covering a new Nebius service stops being a new hand-written module.
`src/nebius_mcp/tools/compute.py` is 542 lines for 10 tools, of which
`compute_create_instance` is roughly 170. At v2 the surface is synthesized from
catalog descriptors plus a promotions table, so the 100% coverage number from
v1.0.0 is sustainable rather than a one-time sprint.

On top of those, the capabilities that only make sense once both hold: code
execution, Slurm, and cross-plane workflows no other client can express.

## Scope

### In

- A hosted remote server with OAuth 2.1 and per-caller credential exchange.
- Zero-terminal install through per-platform bundles.
- Progressive tool disclosure.
- Schema-driven tool synthesis.
- soperator and Slurm.
- Sandboxes and code execution.
- Cross-surface composite workflows.
- Approval-queue write mode.
- Tamper-evident audit with SIEM-native sinks.
- Policy as code with pre-flight simulation.
- Continuous multi-region conformance and published SLOs.
- Structural injection resistance.
- Distribution the project does not control, and versioned documentation.
- A self-healing catalog across unknown SDK versions.

### Out

- Telemetry. Still no.
- Anything that requires the server to hold a durable cloud credential. Task 1
  makes that a design constraint, not a preference.

## Tasks

### v2.0.0-T1 — Hosted remote server with OAuth 2.1 and per-caller credential exchange (L)

`server.main()` in the 0.1.0 tree calls `app.run()` with no transport argument,
so every user must be a Python user first. A hosted endpoint makes the audience
everyone with an MCP client. But a v1-style remote server still holds
credentials on behalf of callers, which for a shared deployment is a single
point of total compromise.

Acceptance:

1. Serves RFC 9728 protected-resource metadata at
   `/.well-known/oauth-protected-resource` with the correct `resource` and
   `authorization_servers`, OAuth 2.1 with PKCE, and RFC 8707 resource
   indicators.
2. Validates `aud` against the server's canonical URI and rejects tokens minted
   for other resources. A wrong-audience token gets 401, asserted.
3. Caller identity is exchanged for a short-lived Nebius credential through
   token exchange or workload identity. The server stores no long-lived cloud
   secret, asserted by scanning for any persisted credential outside a
   per-request context.
4. Scopes map to policy profiles: a token carrying only a read scope sees no
   write tool in `list_tools()`.
5. The authenticated subject appears as `principal` in every audit line.
6. Two tenants are proven isolated at the SDK-construction layer, not merely at
   the parameter layer, by a documented tenant-isolation suite running in CI.
7. `claude mcp add --transport http nebius https://<host>/mcp` connects and
   `iam_whoami` succeeds after a browser consent, on a machine with no Python
   installed. Two different users each get their own identity back.
8. Documented for all five clients, with a threat model covering token custody
   and blast radius, a documented rate limit, and a status page URL.
9. `server.json` gains a `remotes` entry and the registry record shows it.
10. Integration tests against a local mock authorization server cover valid,
    expired, wrong-audience and insufficient-scope tokens.

Files: `src/nebius_mcp/server.py`, `src/nebius_mcp/auth.py`, new
`src/nebius_mcp/oauth.py`, `server.json`, `docs/remote-deployment.md`,
`docs/multi-tenancy.md`, `tests/integration/`.

### v2.0.0-T2 — Zero-terminal install through per-platform bundles (L)

Every install path so far assumes a terminal and a Python toolchain. A
double-clickable bundle reaches people who will never run `uvx`, and it moves
the IAM token out of a plaintext JSON file into the OS keychain — a security win
delivered as a convenience win.

Acceptance:

1. CI builds `.mcpb` bundles for darwin-arm64, darwin-x64, linux-x64 and
   win-x64 with vendored wheels. Per-platform is forced, not chosen: the
   measured runtime tree is roughly 106 MB across 79 packages, with grpc at
   about 38 MB and cryptography at about 23 MB, both shipping platform-specific
   binaries. A universal bundle is not possible and the documentation says so.
2. Each bundle's `manifest.json` declares `server.type: "python"`, an
   `mcp_config` block, and `user_config` entries for the profile, the IAM token
   with `"sensitive": true`, and mode as an explicit enum defaulting to read, so
   write mode is a deliberate toggle in the client's own UI rather than a JSON
   environment variable people paste without reading.
3. `npx @anthropic-ai/mcpb validate` and `pack` pass for each in CI, and the
   bundles are attached to the GitHub release.
4. Manual gate recorded in the pull request: on a clean machine with no Python
   and no uv, double-clicking the bundle installs into Claude Desktop and
   `check_environment` returns `has_credentials: true` after entering a
   profile, with the terminal never opened.
5. `server.json` gains an mcpb package entry per platform with `fileSha256`
   set.

Files: `mcpb/manifest.json`, `.github/workflows/release.yml`, `server.json`,
`docs/`.

### v2.0.0-T3 — Progressive tool disclosure (L)

Even after v0.3.0's toolsets, the enum-heavy generic tools cost a meaningful
share of every request. Every user pays the full catalog cost for a
conversation that touches one resource type.

Acceptance:

1. The server advertises a small starter set and expands the registered surface
   through `notifications/tools/list_changed` after a domain selection or a call
   to `nebius_list_resource_types`.
2. A test asserts the initial `list_tools()` payload serializes to under 4,000
   characters, against roughly 46,000 measured on the 0.1.0 tree, and that every
   generic-reachable operation remains reachable within one expansion step.
3. A byte-budget regression test fails CI when the starter payload grows past
   the threshold.
4. Clients that do not support `list_changed` still see the full surface,
   verified by a capability-negotiation test.

Files: `src/nebius_mcp/server.py`, tool modules,
`tests/unit/test_disclosure.py`.

### v2.0.0-T4 — Schema-driven tool synthesis (L)

Acceptance:

1. New `src/nebius_mcp/synth.py` generates typed tools from
   `catalog.request_class(...).get_descriptor()` plus a per-resource
   `PROMOTIONS` table declaring which verbs get resource-shaped tools and which
   validators apply.
2. `compute.py`, `k8s.py`, `vpc.py`, `registry.py` and `ai.py` shrink to
   promotion declarations. Total line count under `src/` drops by at least 30%
   from its v1.0.0 value.
3. `list_tools()` count and every input schema stay behaviourally equivalent,
   enforced by a golden-file test against the v1.0.0 manifest that permits
   description-text edits only.
4. A test adds a fixture `ResourceSpec` plus one `PROMOTIONS` line at runtime
   and asserts working typed list, get, create, update and delete tools appear
   with no other code change.

Files: `src/nebius_mcp/synth.py`, all tool modules, `tests/golden/`,
`tests/unit/test_synth.py`.

### v2.0.0-T5 — soperator and Slurm lifecycle (L)

soperator is Nebius's differentiator for large-scale training and the one
workload where users cannot fall back on generic Kubernetes knowledge. Today it
is reachable only as an opaque Helm release the agent must hand-construct.

Acceptance:

1. Built on the existing `applications.k8s_release` catalog entry
   (`src/nebius_mcp/catalog.py:301`, `K8sReleaseServiceClient`, v1alpha1).
2. `soperator_install(cluster_id, worker_node_group_id, partitions,
   filesystem_id, nccl_settings, ...)`, `soperator_get_status(cluster_id)`,
   `soperator_list_jobs(cluster_id)` and `soperator_uninstall(cluster_id)`
   registered; install and uninstall behind `preview_or_execute`.
3. `soperator_install` validates that the target cluster has at least one GPU
   node group **and** a mounted `compute.filesystem` before issuing the release,
   failing with a message naming the missing prerequisite and issuing zero
   release RPCs, asserted with stubs.
4. A gated nightly integration test installs soperator on a two-node cluster,
   polls to ready, submits a trivial batch job, asserts it reaches a completed
   state, and uninstalls, leaving zero releases.
5. `README.md`'s v1.0.0 gap statement about soperator is removed in the same
   pull request.

Files: `src/nebius_mcp/tools/soperator.py`,
`tests/integration/test_soperator.py`, `README.md`.

Note: acceptance item 4 requires a standing two-node GPU cluster budget. Confirm
the budget before starting; this is the reason the item is not in v1.0.0.

### v2.0.0-T6 — Sandboxes: code execution as a first-class surface (L) — **DROPPED**

> **This task is dropped and should not be picked up.** Nebius ships
> `contree-mcp` first-party (0.3.0 on PyPI, 17 tools, plus `contree-cli` and a
> Python SDK), so this would reimplement a vendor-maintained server. It is also
> the wrong shape for this server's gates — see
> [v0.4.0-tokenfactory.md](v0.4.0-tokenfactory.md), "Out, deliberately". The
> original text is kept below so the reasoning that produced it stays legible.


Sandboxes turn Nebius from where the model runs into where the agent's code
runs. That is the highest-leverage capability an MCP server can hand an LLM,
and the one with the sharpest safety requirements, which is why it lands after
the confirm, audit and sanitize machinery has been proven across both
credential planes.

Acceptance:

1. `sandbox_create`, `sandbox_exec`, `sandbox_upload`, `sandbox_download`,
   `sandbox_list` and `sandbox_delete` registered, with every path verified
   against a live tenant and recorded in `docs/token-factory-api.md` with its
   verification date.
2. `sandbox_exec` output passes through `sanitize.wrap()` and is capped at
   64 kB with a truncated flag. A unit test asserts a 1 MB stdout is truncated,
   not returned.
3. Sandboxes are created with a mandatory TTL, default 3600 seconds and hard cap
   86400, and `sandbox_list` surfaces `expires_at`, so a leaked sandbox cannot
   outlive the day.
4. `sandbox_exec` is write-mode gated through `require_write()`, subject to the
   policy file, and logged by the audit middleware with a hash of the command
   arguments.
5. An integration test creates a sandbox, runs a trivial program, asserts the
   expected stdout, deletes it, and asserts a subsequent get returns not-found.

Files: `src/nebius_mcp/tools/sandbox.py`, `docs/token-factory-api.md`,
`tests/`.

### v2.0.0-T7 — Cross-surface composite workflows (L)

The reason to hold both planes in one server is that an agent can go dataset to
fine-tune to dedicated endpoint to live inference, or dataset to Slurm job to
checkpoint in object storage, as a single plan. No other client can express
these, because no other client holds both the gRPC control plane and the Token
Factory REST plane behind one credential resolver.

Acceptance:

1. `nebius_finetune_and_deploy(dataset_path, base_model, endpoint_name, ...)`
   chains upload, create fine-tuning job, poll to terminal, create dedicated
   endpoint, smoke chat completion, returning
   `{file_id, job_id, model_id, endpoint_id, sample_output}`.
2. `nebius_train_on_slurm(cluster_id, dataset_uri, sbatch_script,
   checkpoint_bucket)` chains job submit, poll, and checkpoint sync to a storage
   bucket.
3. Both expose a single full-plan `preview_or_execute` dry run enumerating every
   step with estimated cost and expected wall-clock.
4. Both are resumable: given a job or run identifier from a prior partial run
   they skip completed steps, asserted with stubs recording which steps
   re-executed.
5. A gated nightly integration test runs the full fine-tune-and-deploy chain on
   a small dataset, asserts a non-empty sample output, tears everything down,
   and asserts zero surviving files, jobs or endpoints.

Files: `src/nebius_mcp/tools/workflows.py`, `tests/integration/`.

### v2.0.0-T8 — Approval-queue write mode (L)

Every control up to here still ends with the agent holding the delete
capability and something guarding it. The step change is removing the
capability.

Acceptance:

1. `NEBIUS_MCP_WRITE_MODE=queue`: destructive tools enqueue a change request and
   return its id instead of executing.
2. Requests are dispatched to a configurable approver channel — webhook, chat,
   or a REST endpoint — carrying a rendered human-readable diff of what would
   change.
3. Execution happens out of band through a separate approver-authenticated
   path. The MCP process never calls the destructive SDK method itself,
   asserted by a test that monkeypatches the delete call and proves it is
   unreachable in queue mode.
4. Approval, rejection and expiry are audit-logged with approver identity.
5. End-to-end tests cover propose to approve to execute, and propose to reject
   to no-op.

Files: `src/nebius_mcp/queue.py`, `src/nebius_mcp/confirm.py`, `tests/`.

### v2.0.0-T9 — Tamper-evident audit with SIEM-native sinks (L)

An audit log an attacker can edit is a log you cannot testify from.

Acceptance:

1. Each audit record carries a hash chained to its predecessor.
   `nebius-mcp audit verify <file>` detects any insertion, deletion or edit;
   test by mutating one byte mid-file and asserting a non-zero exit naming the
   broken link.
2. Pluggable sinks — file, syslog RFC 5424, OTLP, and object storage — each
   configurable and tested.
3. Records emit in an OCSF-compatible shape so they map into common SIEM
   tooling without a custom parser.
4. Backpressure and sink-failure behaviour is documented and tested. A failing
   sink must not silently drop events, and `NEBIUS_MCP_AUDIT_FAIL_CLOSED=1`
   refuses tool calls when the sink is down.
5. Optional OpenTelemetry export with a span per MCP tool call containing a
   child span per gRPC call, carrying the Nebius request id and trace id as span
   attributes, plus a Prometheus endpoint on the HTTP transport exposing tool
   call counts, durations, retries, throttled seconds and operation wait times.
   Off by default. A redaction test asserts no resource name, id or secret ever
   becomes a metric label. A checked-in Grafana dashboard JSON ships under
   `docs/`.

Files: `src/nebius_mcp/audit.py`, `src/nebius_mcp/sinks/`,
`docs/audit-schema.md`, `docs/grafana-dashboard.json`, `tests/`.

### v2.0.0-T10 — Policy as code with pre-flight simulation (L)

Security teams approve diffs, not vibes. Today the only way to learn what an
agent could do is to let it try.

Acceptance:

1. `nebius-mcp policy test --policy p.yaml` statically enumerates every
   reachable operation across all catalog resource types and derived verbs,
   split into read, state-change and irreversible.
2. `nebius-mcp policy diff old.yaml new.yaml` shows exactly which operations a
   change adds or removes.
3. Optionally intersects with the caller's live IAM grants to report effective
   rather than nominal capability.
4. Output in both human and JSON form.
5. A worked CI example fails a pull request that widens destructive reach
   without an explicit approval label.

Files: `src/nebius_mcp/policy.py`, `src/nebius_mcp/server.py`, `docs/`,
`tests/`.

### v2.0.0-T11 — Continuous conformance and published SLOs (L)

A release-time conformance run proves it worked on one tenant on one day. Users
hit empty projects, projects where pagination actually matters, and
restricted-IAM projects where half the calls are permission denials — shapes a
single CI tenant never exercises.

Acceptance:

1. Conformance runs hourly against at least two Nebius regions and at least
   three tenant shapes: an empty project; a project with over 500 resources
   across at least five types; and a project with a deliberately restricted
   service account.
2. Results land on a public status page with per-tool 30-day pass rate and p50
   and p95 latency. Any tool dropping below 99% trailing-24-hour pass rate
   auto-opens an issue tagged with region and tenant shape.
3. `docs/RELIABILITY.md` publishes SLO targets measured from that run, and
   `release.yml` blocks a tag when the trailing-7-day error budget is
   exhausted, with a documented override requiring an explicit justification
   line in `CHANGELOG.md`.
4. A scheduled 24-hour soak against a live tenant with hourly token rotation,
   forced gRPC channel resets every 15 minutes and injected 30-second network
   partitions every 2 hours asserts zero unrecovered tool calls, zero leaked
   cloud resources at teardown, resident memory growth under 10%, and every
   recovery event visible in the audit log with attempt count and error code.
5. A 50-requests-per-second, 10-minute load test against the HTTP transport
   shows no file-descriptor or memory growth, and graceful shutdown drains
   in-flight operations and reports abandoned operation ids.

Files: `.github/workflows/conformance.yml`, `docs/RELIABILITY.md`,
`tests/integration/`.

### v2.0.0-T12 — Structural injection resistance (L)

`DATA_PREAMBLE` asks the model not to follow instructions embedded in API
responses. Asking is not a control; a sufficiently persuasive payload wins.

Acceptance:

1. Every string in a tool response is tagged with its provenance —
   server-authored or cloud-sourced — in the response structure.
2. Cloud-sourced free-text fields (names, descriptions, labels, annotations,
   error text) are length-capped, control-character-stripped, and delivered in a
   structurally distinct position from server-authored guidance.
3. The v1.0.0 injection corpus grows to at least 100 payloads including
   multilingual, encoded and homoglyph variants, and CI asserts a measured
   resistance rate against a defined baseline.
4. An evaluation harness under `tests/security/` reports the rate as a tracked
   metric per release, published in `SECURITY.md`.
5. `docs/injection-model.md` documents the mechanism and states the residual
   risk explicitly.

Files: `src/nebius_mcp/sanitize.py`, `tests/security/`,
`docs/injection-model.md`, `SECURITY.md`.

### v2.0.0-T13 — Distribution the project does not control, and versioned docs (M)

Self-published links only reach people already looking at this repository. And
after a major bump, a user pinned to 1.x who lands on the documentation site
gets 2.x tool names and silently broken instructions.

Acceptance:

1. Listed in at least two properties the author does not own, verified by URL:
   one Nebius-controlled property — documentation, the GitHub organization, or a
   Nebius-authored post — and at least one aggregator directory. Each listing
   links the same published documentation and states the manifest sha256.
   Install-from-directory is verified end to end on each client and recorded as
   new rows in `docs/COMPATIBILITY.md`.
2. The documentation site serves per-version tool reference paths generated from
   each tagged release's `manifest.lock.json`, with a version switcher and an
   unversioned latest alias. A banner on any non-latest page states the version
   and links the current one. Old majors stay reachable for two majors, stated
   in the versioning policy. Verified by fetching a v1 path and a latest path
   and asserting each lists that version's tool names.
3. The relationship between this server and the separate Nebius and Token
   Factory skills is stated in one compatibility table published in all three
   repositories, so a user with both installed does not silently bypass this
   server's validation, write gate and sanitizer by shelling out to the CLI.
   With this server and the updated skill both installed, prompts that map to
   covered capabilities resolve to MCP tool calls, and only documented gaps
   produce a shell-out.

Files: `docs/`, `README.md`, `docs/COMPATIBILITY.md`, `docs/adoption.md`.

### v2.0.0-T14 — Self-healing catalog across unknown SDK versions (L)

The `nebius<0.5` pin is a dam, not a solution. It converts every SDK improvement
into a manual migration and eventually strands users on an old API. Worse,
`generic.py` builds its resource-type literal from `catalog.RESOURCES` at import
time, so one failing client-class import takes the whole registration down and
the server exposes zero tools instead of most of them.

Acceptance:

1. `catalog` collects per-resource resolution failures into a degraded mapping
   instead of raising. The server starts with the surviving resource types, and
   `check_environment` reports `degraded_resource_types: [{key, reason}]`.
2. A test monkeypatches one module import to raise `ImportError` and asserts
   `_build_app()` still succeeds, still registers all generic tools, and exposes
   the remaining resource types with the failure named in `check_environment`.
3. The dependency pin widens with runtime capability probing. On an SDK version
   outside the tested set the server derives the catalog dynamically, sets
   `catalog_source: probed`, and reports a per-resource-type confidence in
   `check_environment` and `nebius_list_resource_types`.
4. The `sdk-matrix` job runs the contract and conformance suites against three
   consecutive `nebius` minors. The acceptance bar is zero user-visible tool
   loss across a minor bump, asserted by diffing the manifest tool list between
   SDK versions.
5. Continuous supply-chain assurance: CI rebuilds each release from the tag in a
   clean environment and asserts a byte-identical wheel; SBOM diffing surfaces
   added, removed and version-changed components in the release notes; VEX
   statements are published for advisories that do not affect this project; a
   weekly job re-audits the current release's SBOM against fresh advisory data;
   and OpenSSF Scorecard runs in CI with a documented minimum score gate.

Files: `src/nebius_mcp/catalog.py`, `src/nebius_mcp/tools/generic.py`,
`src/nebius_mcp/tools/ops.py`, `pyproject.toml`,
`.github/workflows/{ci,nightly,release}.yml`, `tests/unit/test_degraded_catalog.py`.

## Files likely touched

The whole tree. Structurally: new `src/nebius_mcp/{oauth,synth,queue,sinks}.py`
and `tools/{soperator,sandbox,workflows}.py`; a rewrite of every hand-written
tool module into promotion declarations; `catalog.py` for probing; `audit.py`
and `sanitize.py` for the audit chain and provenance tagging; the documentation
site for versioning; `mcpb/` and `server.json` for distribution.

## Risks

- **T1 is a service, not a feature.** A hosted endpoint carries uptime,
  on-call, abuse handling and cost obligations that no acceptance criterion
  captures. Decide whether the project is willing to operate one before
  starting; if not, ship the transport and let others host it, and say so.
- **T5, T6, T7 and T11 all require standing paid infrastructure** — a two-node
  GPU cluster, sandbox capacity, fine-tuning runs, and hourly multi-region
  conformance. Confirm budget before starting each; an unfunded nightly is a
  permanently red check, which is worse than no check.
- **T4 rewrites every tool module while T5, T6 and T7 add new ones.** Sequence
  T4 either strictly before or strictly after the new surfaces, never
  concurrently.
- **T3 and T4 both change what `list_tools()` returns**, which the v1.0.0 lock
  file freezes. Both require an explicit major-bump entry through
  `scripts/bump_manifest.py`; neither may edit the lock file directly.
- **T12 can degrade usability.** Length-capping and control-character stripping
  of cloud-sourced strings will change what users see in legitimate resource
  descriptions. Measure that alongside the resistance rate.
- **T14 widens the dependency pin.** The probing path must be proven to lose
  zero tools before the pin moves, not after.

## Definition of done

- A team shares one URL; each member's `iam_whoami` returns their own identity;
  and a scan of the running process finds no persisted cloud credential outside
  a per-request context.
- Covering a new Nebius service is a data change: the fixture test in T4 passes
  with one added `PROMOTIONS` line and no other code.
- The initial `list_tools()` payload is under 4,000 characters and every
  operation stays reachable within one expansion step.
- soperator installs, runs a job to completion and uninstalls in the nightly,
  leaving zero releases; a sandbox is created, executed in and destroyed in the
  integration suite.
- In queue write mode, a test proves the MCP process cannot reach the
  destructive SDK method at all.
- `nebius-mcp audit verify` detects a single mutated byte.
- "Is nebius-mcp working right now" has a public, data-backed answer with
  per-tool pass rates across at least two regions and three tenant shapes.
- Versioned documentation serves 1.x tool names at 1.x paths after 2.0.0 ships.
