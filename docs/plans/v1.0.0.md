# v1.0.0 — Recommend it to strangers

Read [../ROADMAP.md](../ROADMAP.md) first. This release assumes v0.4.0 shipped.

## Goal

The bar for 1.0 is four things holding at once. Nothing a competent user wants
is answered with "go use the console." Every one of those capabilities has been
executed against a real tenant on the exact commit being tagged. The artifact a
stranger installs is verifiable. And the surface they build against is under a
written contract that a rename cannot silently break.

This is the release where claims stop being self-assessed and start being
mechanically enforced. The tag itself is blocked if the live conformance run is
not green.

## Scope

### In

- 100% catalog reachability, enforced.
- Full-surface live conformance, including the write path, gating the tag.
- Composite deploy tools.
- The remaining Token Factory surfaces: batch, dedicated endpoints, Data Lab.
- Session-scoped state, and a loopback-only HTTP transport.
- MCP elicitation as a real human decision point.
- A verifiable supply chain.
- A frozen tool surface with a committed lock file.
- MCP resources and prompts, and a manifest that covers them.
- A documentation site with a generated tool reference.
- A verified onboarding matrix, `doctor`, and platform truth including Windows.
- Failure injection over the reliability core.
- An executable release gate, and an adoption gate on the tag.

### Out, deliberately, and stated in the README as gaps

- **soperator and Slurm.** Nebius's headline differentiator for large-scale
  training. Its acceptance requires a gated nightly install on a real two-node
  GPU cluster, which is a standing cost and an operations commitment. v2.0.0.
  The README must say so rather than implying coverage.
- **Sandboxes and code execution.** v2.0.0.
- **A hosted remote service, OAuth 2.1, and per-caller credential exchange.**
  v2.0.0. This release ships loopback HTTP only.
- **Progressive tool disclosure.** v2.0.0.
- **Schema-driven synthesis of the hand-written tool modules.** v2.0.0.
- **Telemetry.** Never. See the decision in `../ROADMAP.md`.

## Tasks

### v1.0.0-T1 — 100% catalog reachability with a CI-enforced coverage report (M)

"What can this server do on Nebius" is currently answerable only by reading
source. A stranger needs a number they can check, and the project needs an
alarm when an SDK bump adds operations nobody wired up.

Acceptance:

1. `scripts/coverage_report.py` writes `coverage.json`: per resource key
   `{verbs_in_sdk, verbs_reachable, tools}` plus totals
   `{sdk_operations, reachable, percent}`.
2. `tests/unit/test_coverage.py::test_no_unreachable_verbs` fails when any verb
   in `catalog.verbs(key)` has no reachable tool path. It fails on the 0.1.0
   tree against 90 operations and passes here against all 305.
3. `generic.py`'s `_ACTIONS` tuple extends to cover `upgrade`, `purge`,
   `revoke`, `issue` and `estimate`, with `purge` and `revoke` added to
   `_IRREVERSIBLE_ACTIONS`.
4. `get_manifest` gains a coverage block `{sdk_operations, reachable, percent}`.
5. CI fails when the percentage printed in `README.md` disagrees with
   `coverage.json`.
6. `scripts/discover_resources.py` walks `nebius.api.nebius.*` for every class
   ending in `ServiceClient` and diffs against `catalog.RESOURCES`;
   `test_no_undiscovered_service_clients` fails on drift. Deliberate exclusions
   live in an allowlist where each entry carries a reason string, and an empty
   reason fails the test. A weekly job runs the discovery script against the
   latest published `nebius` and opens an issue on drift.

Files: `scripts/coverage_report.py`, `scripts/discover_resources.py`,
`src/nebius_mcp/tools/generic.py`, `src/nebius_mcp/manifest.py`,
`tests/unit/test_coverage.py`, `tests/unit/test_catalog.py`, `coverage.json`,
`README.md`, `.github/workflows/`.

### v1.0.0-T3 — Write-path integration suite with guaranteed teardown (L)

The dangerous half of the surface has never executed once, and the confirm

Acceptance:

1. A session-scoped fixture creates a project named `nbmcp-ci-<run_id>` and

2. The suite runs network → subnet → disk → instance create → start → stop →

3. It asserts the first call does not mutate, and that a token minted for a
   different argument set is rejected.
4. `scripts/reap_ci_resources.py` deletes anything CI-labelled older than six
   hours. The nightly job reports `leaked_resources` and fails when it is
   non-zero.

### v1.0.0-T4 — Composite `nebius_deploy_vm` and `nebius_deploy_gpu_cluster` (L)

Creating a usable GPU VM means chaining network, subnet, optional GPU cluster,
disk and instance while getting `parent_id` semantics right at every step —
which `catalog.ResourceSpec.parent`'s own docstring calls the most common
Nebius API error. Every agent re-derives this and most get it wrong at least
once.

Acceptance:

1. `nebius_deploy_vm(project_id, name, platform, preset, boot_disk_size_gib,
   ssh_public_key, ...)` returns `{instance_id, public_ip, ssh_command,
   created, reused}`.
2. Idempotent by name: re-running with the same name reuses an existing network
   and subnet rather than creating duplicates, asserted with stubs recording
   create-call counts across two invocations.
3. A single `preview_or_execute` gate covers the whole plan; the dry-run
   preview enumerates every resource that will be created.
4. On mid-sequence failure the tool returns
   `{failed_step, created_so_far, rollback_hint}`; with `rollback=true` it
   deletes what it created. An integration test injects a failure at the
   instance step and asserts zero orphaned disks, subnets or networks remain.
5. `nebius_deploy_gpu_cluster` additionally provisions a `compute.gpu_cluster`
   and attaches it where the chosen platform supports InfiniBand, refusing with
   an actionable error where it does not.

Files: `src/nebius_mcp/tools/deploy.py`, `tests/unit/test_deploy.py`,
`tests/integration/test_deploy.py`.

### v1.0.0-T6 — Session-scoped state, and a loopback HTTP transport (L)

`auth.get_sdk()` memoizes one SDK for the process, `client.service()` memoizes
one client per class in a module dict never invalidated, and `confirm._active`
is a module-level dict. Under any HTTP transport those are three correctness
bugs: every caller shares one identity, and a confirm token minted in session A
is redeemable in session B. This must land before remote mode, not after.

Acceptance:

1. A `CredentialContext` carried per request through `contextvars`, with an LRU
   of SDKs keyed by a credential fingerprint — a hash, never the token.
2. `client.service()` resolves through the active context. Confirm tickets and
   client caches are keyed by MCP session identity.
3. `auth.reset_sdk()` calls `client.reset_clients()`; the cache key becomes
   `(id(sdk), client_cls)`.
4. Tests: two concurrent calls under different credential contexts receive
   different SDK instances and different client instances, asserted by
   identity; no client constructed under context A is ever returned under
   context B; ten concurrent `service()` calls construct exactly one client.
5. `tests/integration/test_multisession.py` runs 20 concurrent sessions with
   distinct credentials and asserts zero cross-session confirm-token
   redemptions and that every response's principal matches its own session.
6. stdio behaviour is unchanged — a single ambient context — and the existing
   unit suite passes untouched.
7. `nebius-mcp --transport http` serves `/mcp` over FastMCP streamable HTTP,
   binding `127.0.0.1` by default. Unauthenticated requests get 401 with a
   `WWW-Authenticate` header. Requests whose `Origin` is not allowlisted get
   403, guarding against DNS rebinding. Binding a non-loopback address without
   `NEBIUS_MCP_ALLOW_PUBLIC_BIND=1` exits non-zero with an explanatory error.
   `MCP-Protocol-Version` and session-id handling conform to the spec.
8. An integration test exercises all four HTTP behaviours against a live local
   server.

Files: `src/nebius_mcp/auth.py`, `src/nebius_mcp/client.py`,
`src/nebius_mcp/confirm.py`, `src/nebius_mcp/server.py`,
`tests/unit/test_client_cache.py`, `tests/integration/test_multisession.py`,
`tests/integration/test_http_transport.py`.

### v1.0.0-T7 — Real human-in-the-loop via MCP elicitation (M)

The confirm token is minted and consumed by the same party, so it stops typos
and nothing else. An injected instruction produces two tool calls instead of
one and the delete still happens.

Acceptance:

1. Destructive tools call FastMCP's elicitation API before any SDK call when
   the client advertises the capability. The existing token flow remains as
   fallback.
2. `NEBIUS_MCP_REQUIRE_ELICITATION=1` makes a non-supporting client a hard
   `ToolError` instead of a silent fallback to the self-consumable token.
3. A test with a mock client advertising elicitation asserts the request is
   emitted and that declining it prevents the `client.delete(...)` call.
4. A test with `REQUIRE_ELICITATION=1` and a non-supporting client asserts a
   `ToolError` and that no token was issued.
5. `README.md` and `SECURITY.md` state which clients support this and what the
   fallback costs. `confirm.py`'s docstring, corrected in v0.2.0-T7, is updated
   again to describe the new arrangement accurately.
6. `require_write`'s message uses the client hint to name that client's
   configuration file path and the exact key to add, falling back to a
   five-client list when the hint is absent. A test asserts a file path appears
   for at least two simulated client hints.

Files: `src/nebius_mcp/confirm.py`, `src/nebius_mcp/server.py`,
`tests/unit/test_confirm.py`, `README.md`, `SECURITY.md`,
`docs/WRITE_MODE.md`.

### v1.0.0-T9 — Frozen tool surface and `nebius-mcp verify` (M)

Users are told to pin a manifest hash and to wire tool names into agent
configurations. Without a contract, a description tweak silently invalidates
their pin and a rename silently breaks their automation — and an accidental
drift is indistinguishable from the rug pull the hash is meant to detect.

Acceptance:

1. `manifest.lock.json` is committed, containing the full `build_manifest()`
   output plus its sha256. `manifest.sha256` is committed alongside it.
2. `tests/unit/test_manifest_contract.py` fails when the live manifest differs,
   with a message pointing at `scripts/bump_manifest.py`. That script refuses to
   write unless `CHANGELOG.md` has a `### Manifest` entry for the pending
   version, and refuses a tool removal or rename unless the pending version is a
   major bump.
3. A CI job `manifest-drift` rebuilds and fails on any difference from the
   committed file. Verify by deleting one character from a tool description and
   confirming CI goes red.
4. `NEBIUS_MCP_EXPECTED_MANIFEST_SHA`: when set and mismatched, `main()` exits
   non-zero before serving, printing expected and actual.
5. `nebius-mcp verify` rebuilds the local manifest, compares it to the hash in
   the signed release metadata, and exits non-zero with a per-tool diff.
   `--offline` compares against the committed `manifest.sha256` only. A test
   mutates one tool description in a temporary install and asserts `verify`
   exits non-zero naming that tool.
6. `docs/COMPATIBILITY.md` states which surfaces are covered by SemVer — tool
   names, required parameter names, environment variable names, CLI exit codes,
   `--print-config` output shape — and which are explicitly not — tool
   descriptions, the `get_manifest` sha256, result field ordering. It defines
   the deprecation policy: a deprecated tool keeps working for two minor
   releases, carries a `DEPRECATED:` prefix naming its replacement and removal
   version, and appears under `### Deprecated` in `CHANGELOG.md`. A CI check
   asserts every `DEPRECATED:` tool has a matching changelog entry.
7. Every release publishes `manifest.json` and `manifest.sha256` as assets, and
   the documentation site carries a version-to-sha256 table generated from them.

Files: `manifest.lock.json`, `manifest.sha256`, `scripts/bump_manifest.py`,
`src/nebius_mcp/server.py`, `tests/unit/test_manifest_contract.py`,
`docs/COMPATIBILITY.md`, `.github/workflows/`.

### v1.0.0-T13 — Failure injection over the reliability core (M)

Error handling exercised only on the happy path is not error handling. And
`DATA_PREAMBLE` is the only injection defense in the project, with no fixture
anywhere carrying a payload.

Acceptance:

   no unhandled exception reaching the MCP frame, and no secret in the message.
2. `pytest-cov` added to dev dependencies with a CI-enforced branch threshold of
   at least 90% on `errors.py`, `operation.py`, `pagination.py`, `client.py`
   and `confirm.py`.
3. `tests/security/test_injection_corpus.py` holds at least 20 fixtures placing
   payloads in instance names, labels, descriptions, k8s annotations, registry
   image tags, secret values and API error strings. It asserts every tool
   response — including error responses — is wrapped in the envelope, and that
   no fixture can drive a destructive call without both a policy allow and a
   confirm or elicitation step.
4. A new CI job `security-tests` runs the corpus, and the results are summarized
   in `SECURITY.md` under the tool-poisoning row.

Files: `tests/unit/test_failure_injection.py`, `tests/security/`,

### v1.0.0-T14 — Release QA gate, and the adoption gate on the tag (M)

"We ran the tests" is not a gate if the ordering, the warning policy and the
packaging check are informal. The current suite emits over 300 warnings,
including `coroutine ... was never awaited` — test doubles that never execute
the code they claim to cover — and nobody notices because warnings are not
errors.

Acceptance:

1. `release.yml` requires, in order: unit, stdio-conformance, sdk-contract,
   integration and full conformance green; `ruff` and `mypy --strict` over both
   `src` and `tests`, which are unchecked today; `pytest -W error` passing with
   an explicit allowlist of third-party warnings, with the current warning count
   triaged to near zero; `uv build` plus `twine check`; an install-from-wheel
   smoke where the console script answers initialize, tools/list and ping over
   stdio in a clean virtual environment; `scripts/security_audit.sh` clean; and
   the manifest sha256 recorded in `CHANGELOG.md` and diffed against the
   previous release under an explicit tool-surface-changed section.
2. `docs/RELIABILITY.md` publishes the measurement method and the current
   figures for read-tool and mutation-dispatch latency and non-user-error
   failure rate, sourced from the conformance run.
3. A daily `published-smoke` workflow installs `nebius-mcp` from PyPI — never
   from the checkout, asserted by checking the installed dist-info location is
   outside the workspace — on `ubuntu-latest` and `macos-latest` with an empty
   cache, completes initialize and tools/list, and asserts the recorded tool
   count and manifest sha256. On failure it opens an issue.
4. A test asserts the server makes no outbound network call during
   `_build_app()` and `list_tools()`, and that no HTTP client outside the
   Nebius SDK path and the Token Factory client added in v0.4.0-T3 is used.
   There is no telemetry and there will not be.
5. `docs/adoption.md` is refreshed monthly by a scheduled workflow opening a
   pull request, recording PyPI download counts, repository metrics and
   registry listing status.
6. **Tag gate:** the `1.0.0` tag is held until the package has been on PyPI for
   at least 30 days with a non-zero download trend, and at least one issue or
   pull request has been opened by an account that is not the repository owner.
   If the second condition is unmet, ship `0.5.0` and keep working on
   distribution.

Files: `.github/workflows/{release,published-smoke,adoption}.yml`,
`docs/RELIABILITY.md`, `docs/adoption.md`, `pyproject.toml`.

## Files likely touched

Nearly everything. The structurally significant changes are
`src/nebius_mcp/{auth,client,confirm,server,manifest}.py` for session scoping
and the transport, new `src/nebius_mcp/{resources,prompts}.py` and
`tools/deploy.py`, a full `docs/` site, `manifest.lock.json`, `server.json`,
and four new workflows.

## Risks

- **T2, T3 and T4 all require a funded Nebius tenant with GPU quota, and T3
  creates and destroys real projects.** This is the release's hardest external
  dependency. Land T3's teardown fixture and reaper before any test that
  creates anything.
- **T6 is a rewrite of credential resolution.** It is the module whose last two
  bugs each made the server completely unusable, and unit tests cannot catch
  those because they mock at the service boundary. Require a live multi-session
  test, not only unit assertions.
- **T9 freezes the surface, so it must land after T1, T4, T5 and T10 have
  finished changing it.** Sequence it late.
- **The adoption gate in T14 is a business condition the engineering work cannot
  satisfy.** It can hold the tag indefinitely. That is the intent: shipping
  1.0 to nobody proves nothing. Ship 0.5.0 rather than weakening it.
- **T11 is a large surface of prose that the docs-truth gates must cover.**
  Extend `scripts/check_docs.py` to `docs/` in the same pull request that
  creates the site, not after.
- **`pytest -W error` in T14 may surface real bugs in test doubles.** The
  `coroutine was never awaited` warnings indicate tests that do not execute the
  code they claim to cover. Budget for fixing tests, not only for silencing
  warnings.

## Definition of done

- All 14 tasks meet their acceptance criteria.
- The conformance job is green on the tagged SHA, and `release.yml` provably
  refuses to publish otherwise.
- `coverage.json` reports 305 of 305 and the README percentage matches.
- `gh attestation verify` succeeds against the published wheel, and an SBOM is
  attached to the release.
- `manifest.lock.json` is committed and `nebius-mcp verify` exits 0 against the
  released artifact.
- `docs/COMPATIBILITY.md` has no row older than 30 days and no cell over five
  minutes, including a Windows row and a Linux row.
- The documentation site is live, its tool reference is generated, and the
  coverage gate passes for every registered tool.
- `README.md` names soperator, Sandboxes and hosted remote mode as known gaps
  rather than implying coverage.
- The adoption gate is satisfied, or `0.5.0` ships instead.
